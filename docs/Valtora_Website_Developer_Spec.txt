0. Context for the developer
This site is built in-house (no brand agency at this stage) to launch lean and validate demand. It must look premium enough to sell a £2,000+ product, take refundable deposits, and be flexible enough to change positioning, price, colours, copy - and even the brand NAME - between test rounds. The audience is also under test: we do not yet know whether the winning segment is Western expats, affluent Indian buyers, Emirati/Arab buyers, or new-wealth arrivals. Everything below is built so the answer can come from data and the site can pivot to it.
The five things that matter most
1. Deposit/reserve mechanic (S3) - the primary conversion; tests are worthless without it.
2. Modular, editable everything (S4-6) - copy, price, offer, colours, fonts and NAME changeable without a developer.
3. Per-market sizing (S9.1) - UAE and UK use DIFFERENT size names AND dimensions. A UK King is not a UAE King.
4. Segment delivery via page variants (S5) - the site cannot detect who a visitor is; ad targeting sends each segment to its own variant page, tracked by UTM.
5. Attribution (S8) - UTMs must persist to the deposit record so we can read which segment/territory/name wins.
1. Objectives
Present a premium (AED 8,999-14,999 / £1,999-2,999) mattress brand credibly.
Take a small refundable 'reserve your allocation' deposit as the primary conversion.
Be fully configurable - copy, price, offer, palette, fonts, name - without developer help.
Support duplicated page variants for segment/territory/name testing, each separately tracked.
Display DIFFERENT mattress sizes and dimensions per market (UAE vs UK).
Sell replaceable comfort tops as a standalone product line; support lifecycle emails.
Correct tracking and UTM-to-deposit attribution across Meta, Snap, TikTok, Google.
2. Platform & theme
Shopify (Basic or above). Shopify Markets recommended for UAE/UK regions and currency (confirm vs separate storefronts for maintainability).
Theme: clean premium theme (Dawn baseline or premium), customised for restraint per the Brand Guidelines (whitespace, one serif + one sans).
Critical principle: no hard-coded copy, price, colour, or name anywhere in test surfaces. Everything is a theme setting, section setting, or design token.
3. Core requirement - the deposit / reserve mechanic
Product type: 'Reserve your allocation' - small refundable deposit (default AED 200 / £50, configurable), NOT full price. Via a deposit/pre-order app (e.g. Downpayment, Preorder Now/PreProduct) or native purchase options.
Deposit amount, refundability and terms clearly stated at point of payment.
Capture on deposit: name, email, phone, SIZE (per correct market list), price tier, and the UTM set (see S8). Size data drives the inventory order.
Refundable, with a clear refund path (manual via admin acceptable at launch).
Confirmation email: what was reserved, deposit amount, refundable status, realistic ship window.
Admin export of deposits by size, price tier, and UTM fields.

5. Theming & per-market / per-segment configurability
Colours, fonts and copy must be configurable at three levels: global, per market, and per page-variant. Implement as design tokens, not hard-coded styles.
5.1 Design tokens
All colours as CSS custom properties driven by theme settings: --brand-primary, --brand-accent, --brand-bg, --brand-surface, --brand-ink (defaults per Brand Guidelines: navy 1F3A5F, gold 8A6D3B, off-white F7F5F1, stone EAE6DF, ink 222222).
Fonts as theme settings (serif for headlines, sans for body) - swappable without code.
One place to change globally; the whole site re-skins from the tokens.
5.2 Per-market configuration (UAE vs UK)
Shopify Markets (or separate storefronts) can carry different token values, copy emphasis, sizes, currency and BNPL per market.
Use with restraint: capability is required, but the end-state is ONE brand identity with at most minor market-level accents. Market copy differences (proof-led UK vs exclusivity-led UAE) are expected; wholesale palette divergence is a test-phase tool, not the destination.
5.3 Per-segment delivery (the important mechanic)
How segment targeting actually works
The site cannot detect whether a visitor is a British expat, Indian, or Emirati. Segment delivery happens through PAGE VARIANTS + AD TARGETING: each ad set (segment) links to its own duplicated variant page, carrying segment-tuned copy (and optionally a token override for mood), tracked by utm_content. The ads decide who sees what.
Build requirement: template-level token overrides so a duplicated variant page can carry a different accent/mood without touching the global theme. Segment variants are TEST assets - no winning segment is assumed until Sprint 1 data decides (see S8).

6.9 Voice rules (for anything the developer writes)
Short, confident, sentence case. No exclamation marks. No urgency cliches (hurry, last chance, unbeatable).
Concrete numbers over adjectives (35cm, 7-zone, 100 nights). Always show cm next to size names.
Honest on lead times - honesty reads as premium.
Words to use: engineered, considered, adaptive, refresh, enduring, cool, crafted, allocation, reserve. Avoid: cheap, deal, blowout, revolutionary.

8.3 UTM persistence (the critical build)
Requirement: a small script captures UTMs on landing (first-touch, stored in localStorage/cookie), writes them to cart attributes, so they land on the order/deposit record and appear in the admin export. The deposit app must carry cart attributes through checkout - verify this when choosing the app.
8.4 How the data is read (for the marketing owner)
Spend side: Meta Ads Manager (one ad set per segment = spend per segment); same in Snap/TikTok/Google.
Conversion side: Shopify orders export filtered to the deposit product, pivoted by utm_content (segment) and utm_campaign (territory) = deposits per cell, plus size and price tier.
Join: cost per deposit per cell = ad-set spend / matching deposits. Rank cells; require a minimum (e.g. 5+ deposits) before trusting a cell.
Decision: winning segment + territory takes the budget; the site pivots its base copy/palette to the winner; losing variants are archived, not deleted.

Currency: UAE AED (8,999/11,999/14,999); UK GBP (1,999/2,499/2,999).

Language: UAE English primary, Arabic for ad creative (RTL if an Arabic site version is built). UK English only.
Delivery: UAE local + white-glove; UK proposition per fulfilment route.
SEO: UAE minimal (thin search). UK matters - blog/content capability for cooling + back-pain clusters, schema (Product/Review/FAQ), fast Core Web Vitals.
Consent: UAE banner; UK full GDPR explicit opt-in - non-negotiable.
Analytics weighting: UAE Meta/Snap/TikTok; UK Google/GA4 + Meta.
10. Content & trust (credibility at £2k)
Delivery, refund, lead-time and size-guide pages; honest made-to-order timeline, prominent.
Warranty, trial, secure-checkout badges, contact. Real photography + the unzip-and-swap video (placeholders flagged).
Mobile-first; the deposit flow must be flawless on mobile.
11. What NOT to build
No custom checkout (Shopify's only). No hard-coded copy/price/name/colour in test surfaces.
No SEO-heavy UAE build. No SEO targeting of the Swap System (~0 search demand).
No permanent per-market brand forks - tokens and settings, not divergent codebases.
No native app or loyalty system at launch.
12. Acceptance criteria
Customer selects the correct market size (cm shown), pays a refundable deposit, receives confirmation with lead time and refund terms - flawless on mobile.
UAE visitors see UAE sizes; UK visitors see UK sizes; dimensions always shown.
Marketing can change headline, price, offer, palette tokens, fonts, and brand name/logo without a developer.
Marketing can duplicate the page into segment/territory/price/name variants; each variant can carry a token override.
UTMs persist to the deposit record; the export shows utm_campaign/utm_content per deposit alongside size and tier.
Deposit events fire to Meta, Google (+Snap/TikTok UAE) with value.
Replacement tops purchasable standalone with market-correct sizes.
UAE: AED + Tabby/Tamara. UK: GBP + Klarna/Clearpay + GDPR consent.
Fast on mobile (Core Web Vitals green, especially UK).
13. The brand name is NOT final - build for it to change
The name is under test (candidates: Valtora (control), Amara, Nadira, Aeris). The visual identity is designed so a name change touches almost nothing - build to that.
13.1 Render the wordmark, do not upload it
The key build decision
The logo is a wordmark - the name set in a locked typographic system. Do NOT implement it as an uploaded image file. Render it in HTML/CSS from the brand-name theme setting, in the locked typeface, case, tracking and colour. A name change then requires editing one text field, and the mark still looks like the same brand.

13.2 Name as a global token
Brand name stored as ONE global theme setting, referenced everywhere: header wordmark, page titles, meta tags, transactional and lifecycle emails, footer, policy pages, alt text.
Support the SAME page under 2-3 names for live name A/B tests (duplicated variants), each tracked via utm_content.
Do NOT bake the name into image files, checkout settings, hard-coded strings, or anything needing a rebuild to change.
Acceptance test: changing the brand-name setting updates the rendered wordmark and every reference site-wide, with no image edit and no code change.
